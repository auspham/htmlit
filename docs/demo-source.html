MIGRATION PLAN

Should we migrate auth to the new identity service?

A phased plan with the risk trade-offs and a rollout diagram.

Short answer: yes, but in three phases, not one. The current monolith signs its own sessions, so a big-bang cutover would invalidate every logged-in user the moment we flip the switch. A dual-write phase lets the new identity service take over gradually while the old path stays a safe fallback, so we never have a window where nobody can log in.

Recommendation. Start with a dual-write phase: mirror new sessions into the identity service while the monolith still owns reads. Promote reads only once parity holds for a week.

Rollout

Each phase is independently reversible. The rollback edge below is the important one: if parity checks fail during cutover, we fall straight back to the monolith with zero data loss.

Why not cut over in one pass?

The monolith mints opaque session tokens that only it can validate. Until the identity service has been mirroring those sessions long enough to prove parity, a single cutover is a coin flip on every active login. The extra phase buys us a clean rollback for the price of a week of dual-write.

def issue_session(user, dual_write=True):
    token = identity.mint(user)          # new service is the source of truth
    if dual_write:
        legacy.mirror(user, token)       # keep the monolith warm as a fallback
    return token
